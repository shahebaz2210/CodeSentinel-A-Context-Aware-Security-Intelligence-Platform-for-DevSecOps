# Database.md — CodeSentinel

> **Scope note:** The source document describes the *role* of each data store and the *conceptual* data being tracked, but does not provide a formal schema (table names, columns, types, indexes, or relationships). This document captures only what is explicitly stated or directly implied by the described data structures. It does not invent a schema.

## 1. Data Stores

### 1.1 PostgreSQL — Structured Application & Security State
**Explicit purpose (Section 10 & 11):** "PostgreSQL stores structured application and scan state" and "PostgreSQL stores historical security information so that CodeSentinel can compare scans and identify security trends."

Conceptual entities implied by the source:
- **Repository** — the scanned GitHub repository.
- **Scan** — an individual Repository Scan or PR Scan event, tied to a repository, producing a set of Findings + a Score.
  ```
  Repository
   ├── Scan 1 → Findings + Score
   ├── Scan 2 → Findings + Score
   └── Scan 3 → Findings + Score
  ```
- **Finding** — the normalized output of the scanner layer. The example structure given (Section 8) is:
  ```json
  {
    "finding_id": "F-1024",
    "tool": "semgrep",
    "type": "SQL_INJECTION",
    "severity": "HIGH",
    "file": "src/auth/login.js",
    "line_start": 42,
    "line_end": 42,
    "message": "Potential SQL injection"
  }
  ```
- **Repository Context** — structured metadata produced by Agent 1 (Section 6):
  ```json
  {
    "languages": ["JavaScript", "TypeScript"],
    "frameworks": ["React", "Node.js", "Express"],
    "database": ["PostgreSQL"],
    "authentication": ["JWT"]
  }
  ```
- **Risk Factors / Risk Score** — output of the Risk & Validation Agent + Deterministic Risk Engine, derived from severity + exploitability + confidence + exposure + business impact.
- **Finding Status over time** — the source explicitly requires the ability to classify a finding, scan-over-scan, as: New, Resolved, Recurring, Unchanged, plus aggregate Security Improvements / Security Regressions.
- **Policy Gate Result** — PASS / WARNING / BLOCK outcome per scan.

> **Not specified**: exact table/column names, primary/foreign key design, indexing strategy, data types, migrations approach, or whether Finding history is stored as full row-per-scan snapshots vs. a diffing/event model. These require a schema design pass before implementation.

### 1.2 Qdrant — Vector Database (RAG Layer)
**Explicit purpose (Section 10):** "The vector database is primarily used for the security knowledge/RAG layer. It should not be treated as a replacement for PostgreSQL."

What is stored:
- Embedded representations of curated security knowledge: OWASP guidance, CWE information, secure-coding guidance (Section 9).
- Pipeline: Document Processing → Chunking → Embedding Model → stored in Qdrant.
- At query time, a **Finding** is converted into an embedding and used to perform similarity search against this knowledge base, returning "Relevant Security Documents."

> **Not specified**: collection/index naming, vector dimensionality, embedding model choice, chunk size strategy, metadata filtering fields, or re-indexing/versioning strategy for the knowledge base.

## 2. Data Flow Between Stores
```
Finding (from PostgreSQL) → Embedding → Qdrant similarity search
   → Relevant Security Documents (OWASP/CWE/Secure Coding Guidance)
   → passed to LLM as grounding context
   → LLM output (explanation, risk reasoning, remediation) → persisted back to PostgreSQL
```

## 3. Design Principles (explicitly stated)
- PostgreSQL = structured, relational, transactional state (application + historical security memory).
- Qdrant = semantic retrieval only, not a system of record for application state.
- The final numerical risk score must be computed deterministically by the backend, not freely generated by the LLM — implying risk factors must be stored as structured, queryable data (not just embedded in free text).

## 4. Open Items Requiring Further Definition
- Formal ER diagram / table schema for Repository, Scan, Finding, RiskFactor, PolicyResult entities.
- Retention policy for historical scans (how many scans / how long kept).
- Whether Finding diffing (new/resolved/recurring/unchanged) is computed at write-time or query-time.
- Multi-tenancy / organization-level data isolation model (not mentioned in source at all).
